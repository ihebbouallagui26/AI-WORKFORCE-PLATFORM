# AI orchestration architecture (Phases C0 and C1)

> **C1 update:** the orchestrator now runs the first real, human-initiated, supervised execution (see §9). The statements below about C0 remain true for everything except §8, whose first items are delivered in C1.

Scope of C0: the **secure foundation** of the Python orchestration engine. No agent is executed, no model is called for a task, no tool runs. C1 (first executable agent), C2 (real tools and MCP authorization) and C3 are built on this base.

## 1. Service boundaries

| Concern | Owner | Notes |
| --- | --- | --- |
| Organizations, users, RBAC, agents, skills, tool grants, provider connections, **audit**, future execution/task/approval records | **Core API (Spring Boot)** | Single source of truth for business data |
| Provider credentials | **Core API SecretStore** (AES-256-GCM, B3) | The orchestrator never stores or reads them from its own storage |
| Graph execution, LangGraph checkpoints, provider/MCP clients | **AI orchestrator (Python)** | Disposable runtime state only |
| Identity of humans | Keycloak + desktop (PKCE) | Unchanged |
| Identity of the orchestrator | Keycloak **service account** (`ai-orchestrator`, client credentials) | Separate from every human and from the desktop client |

The orchestrator **never touches Core API business tables**: it has no credentials for that database and talks to the business backend only through typed HTTP contracts. Its PostgreSQL role owns a different database that the Core API role cannot read either.

```
Angular/Electron ──► Core API ◄──── (client credentials, internal endpoints) ──── AI orchestrator
                       │  business data, RBAC, audit, SecretStore                    │ LangGraph runtime + checkpoints
                       ▼                                                             ▼
              PostgreSQL ai_workforce                                    PostgreSQL ai_orchestrator (own role)
```

The desktop does **not** call the orchestrator and the orchestrator never accepts a desktop or user token (its callers are allow-listed service clients; a token whose `azp` is the desktop client is rejected).

## 2. Layout (`services/ai-orchestrator`)

```
app/
  core/            config (pydantic-settings, validated), structured logging + redaction, errors (RFC 9457), caller JWT verification
  api/             FastAPI routes (health, runtime info), middleware (correlation id, size limit, timeout), exception handlers
  clients/         typed Core API client + OAuth2 client-credentials token provider + contracts
  providers/       provider-neutral contracts, secret-safe HTTP engine, Anthropic / OpenAI / Gemini adapters
  orchestration/   state (execution context, typed graph state), graphs (diagnostic), checkpointer (PostgreSQL), runtime
  mcp/             server configuration (closed allowlist), tool registry and permission checks, harmless diagnostic server
```

Stack (pinned in `pyproject.toml`, locked by `uv.lock`): Python ≥ 3.12 (image: 3.13), FastAPI 0.162.7, Uvicorn 0.54.0, Pydantic 2.14.3 / pydantic-settings 2.16.3, HTTPX 0.28.1, structlog 26.1.0, LangGraph 1.2.21 + langgraph-checkpoint-postgres 3.2.0, langchain-core 1.8.0, psycopg 3.3.9, MCP SDK 2.3.0, PyJWT 2.15.1.

## 3. FastAPI foundation

* `GET /health/live`, `GET /health/ready` (public, no details: only `UP/DOWN/NOT_CONFIGURED` per check), `GET /api/v1/runtime/info` (service token required).
* Pure ASGI middleware: **correlation id** (`X-Request-Id` accepted if `[A-Za-z0-9-]{8,64}`, else generated, echoed and put in every log line), **body-size limit** (413), **request timeout** (504). Errors are `application/problem+json`; validation errors never echo the input; unexpected errors are generic and only the exception *type* is logged.
* Lifespan owns every resource (HTTP clients, provider clients, PostgreSQL pool) and closes them on shutdown; Uvicorn runs with a graceful-shutdown deadline.
* Settings come from `AIO_*` environment variables. Secrets are `SecretStr`; production refuses to start without HTTPS endpoints, a client secret and a database URL. API docs are served in `dev` only.
* Default port **8091**: 8090 is occupied by unrelated software on this machine (checked); the port is configurable.

## 4. Identity and authorization

**Orchestrator → Core API.** OAuth2 client credentials with the confidential Keycloak client `ai-orchestrator` (service account only: no browser flow, no password grant, no implicit; access token 5 min; audience mapper adds `ai-workforce-api`). The client secret lives in `infra/docker/.env` (generated by `ensure-env.sh`, never committed) and is installed into Keycloak by `infra/keycloak/scripts/provision-orchestrator-client.sh` (idempotent; works on an existing realm because the realm import only runs once and the realm file must contain no secret). Tokens are cached in memory, renewed before expiry and never logged.

**Core API side** (implemented in C0): a dedicated, first-ordered security filter chain on `/api/v1/internal/**` that accepts only tokens whose authorized party is the orchestrator client (`app.orchestrator.client-id`), granting the single authority `ROLE_ORCHESTRATOR`. The user chain **refuses** that client's tokens (401), so a service token can never be provisioned as a human or used on user endpoints. The only internal endpoint is read-only:

`GET /api/v1/internal/organizations/{organizationId}/agents/{agentId}/execution-context`

It re-validates the pair (organization, agent) — a mismatch is a 404 like for users — serves **ACTIVE agents only** (409 otherwise) and returns a narrow projection: identity, system instructions, VALID provider bindings (connection *ids* and model ids), approved tool grants with MCP coordinates, active skills, memory settings. **No credential or secret reference** is ever part of it.

**Callers of the orchestrator.** `JwtVerifier` validates Keycloak tokens (signature through the JWKS — signing keys only, encryption keys are ignored —, issuer, audience `ai-orchestrator`, expiry) and requires `azp` ∈ `AIO_ALLOWED_CALLER_CLIENT_IDS` (default: a future `ai-workforce-core-api` service client). Everything except `/health/*` needs it.

**Prepared, not served yet (C1/C2).** Contracts for execution status reports, result submission and human-approval requests exist as typed models (`app/clients/contracts.py`) so both sides can be implemented against a reviewed shape. No unrestricted internal endpoint was invented: each future endpoint will be explicit, read/write-scoped and audited by the Core API, which keeps owning every business record.

## 5. Execution identity and tenancy

Every future execution carries an organization id, an agent id, a **server-generated** execution id (UUIDv4), an actor (`user|service|system` + opaque subject id) and allowed capabilities (`ExecutionContext`). These values are validated by the Core API (never trusted from a client). The LangGraph **thread id** is derived on the server as `"{organization_id}:{execution_id}"`.

Isolation in depth:

1. the thread id embeds the organization, so another tenant addressing the same execution id reads an empty thread;
2. after loading, the stored state's `organization_id` must equal the caller's, otherwise `NotFound`;
3. the runtime database is separate, owned by a restricted role (`aiw_orchestrator`: no superuser, no createdb, no createrole) that cannot connect to any other database; checkpoint tables live in the isolated schema `orchestrator_runtime`.

## 6. LangGraph runtime foundation

* Typed graph state (`DiagnosticState`), graph conventions (builder takes the checkpointer; small nodes wrapped by `checked`), `OrchestrationRuntime` with run timeout, cancellation, resume, snapshots.
* **Diagnostic graph** `begin → work×N → finish`: deterministic, no LLM, no shell, no file access. Demonstrates transitions, checkpoint persistence, failure recovery (a fault leaves a checkpoint; `resume(clear_fault=True)` completes it) and **human-in-the-loop** pause/resume (`interrupt_before=("finish",)`).
* **Checkpoint hygiene**: `assert_state_safe` rejects secret-looking keys (`token`, `password`, `api_key`, `credential`, …) and token-looking values (bearer tokens, `sk-…`, `AIza…`, JWTs) on every node update, before LangGraph checkpoints it. Tests read the checkpoint tables and find none. Business records (who ran what, results, approvals) belong to the Core API.
* PostgreSQL checkpoints persist across process restarts (tested with fresh pools).

## 7. Operations

* Docker: image `python:3.13-slim`, multi-stage with `uv sync --frozen`, non-root uid 10001, read-only root filesystem, `cap_drop: ALL`, `no-new-privileges`, health check on `/health/live`. Compose profile `orchestrator`; published on `127.0.0.1` only. Not started by default.
* `db-init` (idempotent, existing volumes preserved) creates the `ai_orchestrator` database and role when `ORCHESTRATOR_DB_*` are present.
* On Windows run the service in Docker or WSL: psycopg's async mode needs a selector event loop, while Uvicorn on Windows uses the proactor loop. The test-suite handles this per module.

## 8. Not in C0

Agent execution, prompts/LLM calls for tasks, tool and MCP execution workflows, approval delivery, execution records in the Core API, trusted credential resolution, usage/cost accounting, retries across providers (fallback orchestration), streaming to the desktop. *(C1 delivered execution, the execution record, trusted credential resolution and usage metadata for Anthropic; the rest remains deferred, see §9.5–9.6.)*

## 9. Supervised execution (Phase C1)

### 9.1 Flow

```
Angular ──POST /agents/{id}/executions {task}──► Core API (user token: membership + agent.execute, agent ACTIVE,
   │  (202, polls GET /executions/{id})            primary binding VALID + Anthropic, org concurrency limit)
   │                                               │ 1. records PENDING (audit: no instruction)
   │                                               │ 2. after commit: POST {orchestrator}/api/v1/executions {organizationId, executionId}
   │                                               ▼    (Core API service account "ai-workforce-core-api", answered 202)
   │                                      Orchestrator (background asyncio task, LangGraph, PostgreSQL checkpoints)
   │                                               │ 3. POST /internal/…/executions/{id}/start      PENDING→RUNNING, returns task
   │                                               │ 4. GET  /internal/…/agents/{id}/execution-context   (C0)
   │                                               │ 5. POST /internal/…/executions/{id}/credential  single use, RUNNING only
   │                                               │ 6. Anthropic Messages API (real adapter)
   │                                               │ 7. POST /internal/…/executions/{id}/complete | /fail
   ▼                                               ▼
 result + history ◄────────────── Core API persists status, result, model, usage, safe error
```

### 9.2 Graph (`orchestration/graphs/execution.py`)

`validate → start → load_context → build_prompt → invoke_model → report → finalize`, with one failure branch `report_failure`. Each stage is wrapped by `guarded`: any exception becomes a safe error code (`PROVIDER_AUTHENTICATION`, `PROVIDER_RATE_LIMIT`, `PROVIDER_TIMEOUT`, `PROVIDER_UNAVAILABLE`, `PROVIDER_BAD_REQUEST`, `PROVIDER_INVALID_RESPONSE`, `CREDENTIAL_UNAVAILABLE`, `AGENT_NOT_ELIGIBLE`, `PROVIDER_NOT_ENABLED`, `PROVIDER_NOT_CONFIGURED`, `CORE_API_UNAVAILABLE`, `CORE_API_REJECTED`, `EXECUTION_TIMEOUT`, `EXECUTION_FAILED`) with a fixed user-facing message; provider and Core API bodies are never copied. The "resolve credential" and "invoke" stages are one node on purpose: the secret never travels between nodes.

State (checkpointed) = organization, execution and agent ids, status, stage, provider and model names, usage counts, error code, step names. **Not** in state: credential, instruction, prompt, result (run-local `RunContext`, wiped when the run ends).

Prompt: system message from the agent's name, handle, system instructions and active skills plus a fixed rule (text only, no tools); user message = the instruction. `max_tokens` = `AIO_EXECUTION_MAX_OUTPUT_TOKENS` (default 1024). Tool grants are **not** interpreted as permission to run tools. No fallback between providers; only `ANTHROPIC` is in `AIO_EXECUTION_ENABLED_PROVIDERS`.

### 9.3 Persistence and status model

Table `agent_executions` (V5): organization-scoped composite keys to `agents` and `provider_connections`, CHECK constraints for the state machine (completion time iff terminal, result only on success, error code iff failed), token usage, correlation id, `credential_resolved_at`. Permissions `agent.execute` and `agent.execution.read` (OWNER/ADMIN only; members and custom roles are not widened). See [ADR-0017](../adr/ADR-0017-supervised-execution-and-credential-issuance.md).

### 9.4 Service-to-service authentication (both directions)

| Direction | Keycloak client | Audience | Accepted by |
| --- | --- | --- | --- |
| orchestrator → Core API | `ai-orchestrator` | `ai-workforce-api` | Core API `/api/v1/internal/**` chain (`azp` = orchestrator client; refused on user endpoints) |
| Core API → orchestrator | `ai-workforce-core-api` | `ai-orchestrator` | orchestrator `JwtVerifier` (`azp` ∈ `AIO_ALLOWED_CALLER_CLIENT_IDS`) |

A user or desktop token is rejected in both places; a service token is rejected on user endpoints. Both clients are confidential, client-credentials only, provisioned by `infra/keycloak/scripts/provision-orchestrator-client.sh`.

### 9.5 Hand-over, recovery and limits

**Hand-over (Core API).** After the launch transaction commits, `ExecutionDispatcher` submits the hand-over explicitly to a bounded pool (`app.executions.dispatch-max-threads`, `dispatch-queue-capacity`; `AbortPolicy`, never caller-runs). The orchestration HTTP call therefore never runs on a request thread. Outcomes: delivered → the orchestrator takes over; pool saturated → the execution is failed immediately with `DISPATCH_CAPACITY_EXCEEDED` (the launch answers `202` with the execution id **and its already-final FAILED state**); delivery error → `ORCHESTRATOR_UNAVAILABLE` **only if the execution is still `PENDING`** (`ExecutionCoordinator.failIfPending`, own transaction, row lock). A RUNNING, SUCCEEDED or FAILED execution is never overwritten by a dispatch error.

**Recovery (reaper).** Every 30 s (`app.executions.reaper-interval-ms`) executions still `PENDING` or `RUNNING` after `app.executions.timeout` (default 5 min, measured from creation) are failed with `TIMEOUT` (`failIfOpen`, same guarded transition). Closing them frees the organization's open-execution capacity (default 3). Worst case before capacity returns after a crash or restart: timeout + one reaper interval (about 5.5 min by default). **C1 does not redispatch**: if the Core API dies between the commit and the hand-over, or the orchestrator restarts mid-run, the execution ends as `TIMEOUT` and the user relaunches. Automatic redispatch is deliberately not implemented: without an idempotency token known to the provider call it could run, and bill, the same instruction twice. Keep `AIO_RUN_TIMEOUT_SECONDS` below `app.executions.timeout`.

**Configuration safety.** The Core API refuses to start if `app.orchestrator.dispatch` is partial or malformed, and outside the `dev`/`test` profiles requires HTTPS for the orchestrator and token URLs (the orchestrator enforces HTTPS for its own endpoints in `prod`).

### 9.6 Limits and deferred work

In-process tasks (no restart survival; the Core API reaper fails them), polling instead of push, no cancellation, no streaming, one provider (Anthropic), no tools/MCP/shell/files, no multi-agent, no approvals, no durable queue. C2: real tools and MCP authorization; C3: collaboration.
