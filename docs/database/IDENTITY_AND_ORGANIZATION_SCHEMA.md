# Identity and Organization Schema

Migration `V2__identity_and_organizations.sql` (Sprint B1). `V1` is unchanged. Sprint B2 adds `V3__workforce_management.sql` (employees, departments, positions, teams): see [WORKFORCE_DATA_MODEL.md](WORKFORCE_DATA_MODEL.md). Conventions: [DATABASE_CONVENTIONS.md](DATABASE_CONVENTIONS.md). All ids are UUID (v7 generated by the application), all timestamps `timestamptz` in UTC.

## Tables

| Table | Purpose | Key constraints |
| --- | --- | --- |
| `user_accounts` | A person using the platform | status `ACTIVE`/`DISABLED`; index on `lower(email)` (not unique: e-mail is not an identity key) |
| `external_identities` | One `(issuer, subject)` from an OIDC provider | **unique `(issuer, subject)`**; FK user |
| `organizations` | Tenant | name 2–100, description ≤ 500, timezone; FK `created_by` |
| `memberships` | User ↔ organization | unique `(organization_id, user_id)`, unique `(organization_id, id)`; status `ACTIVE`/`SUSPENDED`/`REMOVED` |
| `permissions` | Global permission catalog | PK `code`; seeded by V2; read-only at runtime |
| `roles` | Organization roles | unique `(organization_id, id)`, unique `(organization_id, code)`, unique `(organization_id, lower(name))`; `code` ∈ OWNER/ADMIN/MEMBER or null; `built_in = (code is not null)` |
| `role_permissions` | Role → permission | PK `(role_id, permission_code)`; FK `(organization_id, role_id)` → roles **cascade**; FK permission |
| `membership_roles` | Membership → role | PK `(membership_id, role_id)`; FKs `(organization_id, membership_id)` and `(organization_id, role_id)` |
| `organization_invitations` | Pending/accepted/revoked invitation | unique `token_hash`; FK `(organization_id, role_id)`; e-mail lowercase; partial unique `(organization_id, email) WHERE status = 'PENDING'` |
| `audit_events` | Append-only audit trail | index `(organization_id, occurred_at DESC)`; `details` JSON text |

Optimistic locking (`version`) on mutable rows. Composite foreign keys make cross-organization references impossible at the database level.

## Database roles (privilege separation)

Created and maintained by `infra/docker/postgres/init-roles.sh` (idempotent, run by the `db-init` Compose service and by the integration tests):

| Role | Rights | Used by |
| --- | --- | --- |
| bootstrap superuser (`DB_USERNAME`) | everything | `db-init` only (roles, extensions) |
| `aiw_migrator` | owns the `public` schema objects, DDL | Flyway |
| `aiw_app` | `SELECT/INSERT/UPDATE/DELETE` only; no DDL; no access to `flyway_schema_history`; no write on `permissions`; no `UPDATE/DELETE` on `audit_events` | Core API runtime |
| `keycloak` | owner of database `keycloak`; cannot connect to `ai_workforce` | Keycloak |

`afterMigrate.sql` (Flyway callback, run by the migrator) re-applies the runtime grants and revocations after every migration. Extensions (`vector`) need superuser rights and are created by `init-roles.sh`; V1's `CREATE EXTENSION IF NOT EXISTS` is then a no-op.

## Upgrade from B0

On an existing B0 volume: `db-init` creates the roles, the extension and transfers ownership of existing objects (including `flyway_schema_history`) to `aiw_migrator`; Flyway then applies V2 as the migrator. Verified on the real local volume and by `DatabaseSecurityIntegrationTest.migratesAnExistingB0DatabaseToTheCurrentSchema`. No volume is deleted.
