# Workforce Data Model

Migration `V3__workforce_management.sql` (Sprint B2). `V1` and `V2` are unchanged. Conventions: [DATABASE_CONVENTIONS.md](DATABASE_CONVENTIONS.md); concepts: [WORKFORCE_MANAGEMENT_ARCHITECTURE.md](../architecture/WORKFORCE_MANAGEMENT_ARCHITECTURE.md). UUID ids (v7 generated by the application), `timestamptz` in UTC, `version` column for optimistic locking.

## Tables

| Table | Purpose | Key constraints |
| --- | --- | --- |
| `departments` | Hierarchical organizational units | unique `(organization_id, id)`, unique `(organization_id, code)`; code `^[A-Z0-9][A-Z0-9_-]{0,23}$`; status `ACTIVE`/`ARCHIVED`; `parent_id <> id`; FK `(organization_id, parent_id)` → departments; FK `(organization_id, head_employee_id)` → employee_profiles |
| `positions` | Job titles (not authorization roles) | unique `(organization_id, id)`, unique code, unique `lower(title)` per organization; optional FK `(organization_id, department_id)` |
| `employee_profiles` | Professional record of a human employee | unique `(organization_id, id)`; optional FK `(organization_id, membership_id)` → memberships; FKs to positions, departments and manager (`employee_profiles` itself) — all composite; `manager_id <> id`; status `ACTIVE`/`ON_LEAVE`/`INACTIVE`; `end_date >= start_date`; lower-case e-mail |
| `teams` | Collaborative groups | unique `(organization_id, id)`, unique `lower(name)` per organization; optional FKs to department and leader employee (composite) |
| `team_members` | Employees in teams, with history | FKs `(organization_id, team_id)` and `(organization_id, employee_id)`; `left_at >= joined_at`; **partial unique `(team_id, employee_id) WHERE left_at IS NULL`** |

Partial unique indexes on `employee_profiles`: one profile per `(organization_id, membership_id)` and one `(organization_id, employee_number)` (both only where the column is not null). Supporting indexes cover the filters of the API (organization + status / department / position / manager / lower(name)).

## Tenant integrity in the schema

Every table carries `organization_id`, and **every relation is a composite foreign key** `(organization_id, id)`. A row therefore cannot reference a department, position, employee, team or membership of another organization, even when the application is bypassed (tested by writing cross-organization references directly with the runtime role: employee ↔ department / position / manager / membership, department ↔ parent / head, position ↔ department, team ↔ leader, team member ↔ team / employee).

Not expressible as constraints, therefore enforced in services under the organization row lock: no cycle in the department hierarchy, no cycle in reporting lines, a team leader is a *current* member, a manager / head / leader / member is a *current* (not INACTIVE) employee, depth limits.

No `ON DELETE CASCADE`: nothing is deleted by cascade. Employees have no delete endpoint; departments and positions can only be deleted when nothing references them.

## Permission catalog

V3 inserts ten rows into `permissions` and grants them to the built-in roles that already exist:

| Role | Rows added to `role_permissions` |
| --- | --- |
| OWNER, ADMIN | `employee.read`, `employee.create`, `employee.manage`, `employee.deactivate`, `department.read`, `department.manage`, `position.read`, `position.manage`, `team.read`, `team.manage` |
| MEMBER | `employee.read`, `department.read`, `position.read`, `team.read` |
| custom roles | nothing |

The inserts use `ON CONFLICT DO NOTHING`; `BuiltInRole` gives the same sets to organizations created afterwards, and `DatabaseSecurityIntegrationTest.thePermissionCatalogMatchesTheCode` keeps the table and the `Permission` enum identical.

## Privileges and migration paths

- Flyway runs as `aiw_migrator` (owner); the runtime role `aiw_app` keeps **data access only**: `afterMigrate.sql` re-grants DML on the new tables, nothing else. Verified: the runtime role can read/insert but cannot `CREATE`, `ALTER` or `DROP` (clean database and upgraded B1 database).
- **From a B1 database** (V1 + V2 with organizations): `DatabaseSecurityIntegrationTest.upgradesAnExistingB1DatabaseAndBackfillsBuiltInRolePermissions` builds a V2 database with built-in and custom roles, applies V3, then checks the backfill (10 / 10 / 4), that custom roles are untouched, that Flyway validation still passes (checksums of V1–V3) and the runtime privileges. Also verified on the real local volume (existing B1 organization backfilled, no volume deleted).
- **From a clean database**: every integration test starts from an empty PostgreSQL and applies V1 → V3.
- `migratesAnExistingB0DatabaseToTheCurrentSchema` still covers B0 → V3.

## Preparing B3 (AI agents in teams)

`team_members` references `employee_profiles` only. B3 adds a sibling table `team_agent_members (organization_id, team_id, agent_id, …)` with composite foreign keys to `teams` and to the future `agents` table, rather than turning `team_members` into a polymorphic `(member_type, member_id)` relation that no foreign key could protect.
